What this demo assumes

Agent and model: the coding agent and its model are the customer's own — REACHABLE drives whatever agent the enclave already has. Here: opencode, pre-installed, and a hosted model reached only through the gatekeeper. A future product phase could bundle a coding agent + REACHABLE + a local LLM as one turnkey installation; that is not what is demonstrated today.

Keys: this demo self-generates its mirror and enclave-host keys for the Sthenos-owned demo account (a CI preflight-auth step, regenerated on demand; held as stored secrets standing in for a secret manager). A real customer generates theirs through the dashboard — in the browser, so the private key never leaves them, or as short-lived temporary test credentials — needing only a single firewall hole to sthenosec.com, never internet access.

Trust & cryptography: software is admitted into the enclave only from a CNSA-aligned, post-quantum signed attestation; the connection to Sthenos is a mutually authenticated channel; data is encrypted at rest. The highest-assurance trust anchor sits exactly where it matters — on the code entering the air-gapped boundary.

Stand-ins: the package registries are loaded with the application's packages and the fixed versions; the model is remote for the purpose of this test.

Firewall rules on the gatekeeper

The gatekeeper's firewall blocks everything by default (drop). It can reach only Sthenos and the AI model service; the enclave itself has no way out at all. The exact rules:

  1. Replies to connections that are already allowed
  2. The gatekeeper talking to itself
  3. Sthenos — signed software and security updates (encrypted)
  4. Name lookups (DNS) through Docker's own resolver (UDP)
  5. Name lookups (DNS) through Docker's own resolver (TCP)
  6. The AI model provider at 160.79.104.10 (encrypted)

Build a fictional treasury operations portal in the current workspace as a small multi-service system. Model it as a multi-org SaaS with organizations, teams, and users. Use a TypeScript and JavaScript admin portal in portal/, a Go API service in payments-api/, a Python worker or service in docs-worker/, and a Java risk API in risk-api/. Keep each service thin, but make sure each one handles requests through middleware and performs at least one real database query or mutation. Include authentication middleware, role-based access control, audit logging middleware, async payment or settlement jobs, upload and download APIs, risk exposure APIs, a metrics or health endpoint, and local database persistence for organizations, teams, users, accounts, beneficiaries, transfers, risk reviews, and audit records.
